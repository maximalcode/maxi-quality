# Red-team review: the maxi-quality agent guard

## 1. What this is, and what it is not

This is an adversarial review of the agent guard — the three Claude Code hooks and two `permissions.deny` rules in `.claude/settings.json` that stop an agent coding session from ending or committing while the declared quality gate has not verifiably run against the content on disk. It is **not** a review of Layer 1 or Layer 2 (the per-language analyzers and the Semgrep/Gitleaks/OSV umbrella); those are a separate mechanism and were out of scope. It is not an audit of any consuming repository — no consumer was scanned, named, or reached.

**Date:** 2026-08-30. **Method:** five reading agents reconstructed the threat model, the contract README, the hook sources, the 68-case corpus, and the design-history issues; a red-team pass produced fourteen attack claims; each claim was then handed to an **independent verifier** that reproduced (or failed to reproduce) it against the repo's own scripts in throwaway git repositories under a scratchpad, leaving the real repo untouched. Every reproduction line quoted below is the verifier's, run against `scripts/agent-guard/*.py` unmodified. Two concept-level judgements (the invariant, and the #167 measurement contract) were produced separately; §5 and §6 draw on them. Finally, the orchestrating session independently re-reproduced six of the nine confirmed findings from scratch (§4.1, §4.2, §4.4, §4.7, §4.8, §4.9) and independently verified the #167 closure claim in §6 against the GitHub API and the merge commit body, rather than relying on the subagents' reports for any of them. Where a claim in the source notes was a wrong reason for a right decision, it is corrected in place and flagged.

Of the fourteen claims: **nine confirmed as real gaps**, **two refuted** (one of which surfaced a *different* real gap during verification), and **three are restatements of a boundary the design already documents in writing**. Nothing here defeats the guard's *refusal* on the drift it was built for — the confirmed findings are gaps in coverage, in the evidence that the coverage exists, and in one case a fail-open on the exact flag the guard exists to catch.

## 2. The threat model as reconstructed

**Adversary model, as the design states it and as the code bears out: drift, not malice.** The failure the guard exists to stop is "a model that forgets, not one that lies" — a session that partial-runs the gate, edits a file after the gate ran, deletes an expected finding by accident, or reaches for `--no-verify` out of habit. Every plumbing failure fails open (unreadable stdin, not-a-git-repo, git errors, unmodelable edits); only a genuine policy violation blocks. Onto that drift model the design bolts a thin anti-tamper collar at exactly two points — the two `Edit` deny rules — and it is candid that the collar is thin: the receipt-via-shell hole, alias-hides-`--no-verify`, and same-size in-place finding defusal are all conceded in README §3 as undefended by design.

**Trust boundary.** Every input the guard reasons over is session-writable *except* the git object store and the deny array. For the Stop gate the three inputs are the receipt (session-writable via shell), the live fingerprint (git-derived, trusted), and the gate declaration (session-writable); two of three are untrusted, and the integrity claim rests entirely on the fingerprint being one the session cannot forge to match a moved tree. The deny array is enforced by Claude Code before any hook runs, so it is not reachable by the tools it governs — but it covers only the `Edit` tool and only two exact paths, and (finding 2.1) it is loaded from a file the guard's own gate never checks.

The load-bearing consequence of the adversary model for this report: **a bypass that only a hostile or injection-nudged session reaches is a lower-severity finding than one a forgetful session reaches by accident**, because the guard never promised to stop the former. Each finding below is tagged with which class reaches it. Reporting a malice-only bypass as a drift failure would be the exact conflation this repo cares about.

## 3. What the guard demonstrably does

These are the claims backed by code that can be cited or a fixture that pins them; all were confirmed during the reading and verification passes.

- **The source and the enforced copy of the hooks are byte-identical today.** `diff scripts/agent-guard/*.py .claude/agent-guard/*.py` returns clean for all five files; `selftest.py` correctly has no adopted counterpart. (Nothing at runtime *keeps* them identical — see finding 2.1 for the settings file, and `check-agent-contract.py` G9 for the scripts.)
- **The Stop gate blocks on four distinct cases, each with its own message and ledger code:** no receipt (`stop-01`), failing verdict (`stop-04`), a receipt for something that is not the declared gate (`stop-17`), and a stale fingerprint (`stop-03`). `stop-gate.py:main()` steps 7–11.
- **The fingerprint is taken before the gate command runs** (`record-gate.py` step 6), so a formatter-shaped gate cannot certify its own rewritten output; `stop-14` pins the deterministic-formatter-produces-stale-receipt case.
- **`is_declared_gate()` refuses to accept a bare-argv match when the declaration contains a `SHELL_OPERATORS` token** (`guard.py:372`), so a receipt recording only the first half of `a && b` cannot pass as the whole gate. `stop-15`/`stop-16` pin the `&&` case. (Finding 1.3: the token set is incomplete — it omits the newline.)
- **`sample-guard.py` denies manifest finding-removal and cited-fixture line-removal** (`edit-01`, `edit-03`, `edit-05`) and allows everything it cannot model (`edit-08`..`edit-13`), on its stated principle "refuses on evidence, never on ignorance."
- **`no-verify-guard.py` denies `--no-verify` on commit and push and `-n` on commit, and deliberately allows `git push -n`** because `-n` on push is `--dry-run` (`noverify-01/02/04/07`).
- **The two deny rules are structurally asserted** by `selftest.py`'s permissions mode (`deny-01/02/03`) and were **live-confirmed** once, dated 2026-08-23 on Claude Code 2.1.236 (README §5a): a denied `Edit` on the receipt refuses, an empty deny-list on the same file only prompts, and the `/`-anchor is root-only (a nested `sub/samples/expected/…` succeeded).
- **Every Stop exit appends one JSONL ledger row of codes and counts only** — `ts`, `outcome`, `blocked`, `changed`, `session` — never a path, command, or branch; the corpus asserts the **key set** (`stop-26`..`stop-29`). This is the "no cleanup pass" rule made mechanical. (Findings 3.x: the key-set check does not check value *shapes*, and the paste-safe `--summary` path has no fixture at all.)

The core enforcement — the invariant and its receipt, the two deny rules, the `-n`-on-push discrimination — is sound and, for the drift it targets, does what it claims.

## 4. Findings

Ordered by severity, where severity weights **drift-reachability** and **absence of a backstop** most heavily. All nine below carry the verifier verdict **CONFIRMED**; none were left at PLAUSIBLE (every claim was reproduced or refuted outright). Restatements of the documented boundary are in their own subsection at the end.

### 4.1 The enforced `.claude/settings.json` is never checked against its source; both deny rules and the sample-guard matcher can be gutted with the gate green
**Severity: high. Drift-reachable class; no backstop but human review. Corpus case: not expressible — needs a new `check-agent-contract.py` G-check.**

The repo's declared gate is `selftest.py && check-agent-contract.py`, and it is the *sole* structured evidence for the deny rules, which cannot be exercised from a fixture. Both commands validate the **source template** `configs/agent/settings.json` and never the file Claude Code actually enforces. `selftest.py:54` hardcodes `FRAGMENT = configs/agent/settings.json`; `check-agent-contract.py:200` sets `cfg = configs/agent` so G1/G2 (wiring/matchers) and G5 (deny array) all read the template; G9 (lines 652–714) byte-compares only the copied `.claude/agent-guard/*.py` against `scripts/agent-guard/*.py`. Grep confirms `check-agent-contract.py` contains **zero** references to `.claude/settings.json`. That file is itself Edit-tool-editable — it is absent from its own deny array (which lists only the receipt and `samples/expected`), and no hook watches it.

Reproduction (verifier, on a full copy of the repo): baseline `selftest.py` → `cases=68 failed=0`; `check-agent-contract.py` → `OK`. After emptying the deny array **and** narrowing the sample-guard matcher from `Edit|Write|MultiEdit` to `Edit` in the *enforced* file only: both commands still green. The control — the identical mutation applied to `configs/agent/settings.json` instead — fails selftest (3 cases) and prints four `::error::` lines. The asymmetry is exact: source checked, enforced instance invisible. The verifier further checked CI: every `.claude/settings.json` reference in `ci.yml` reads throwaway `/tmp` adoption repos, never this repo's own tracked file, so a committed gut passes full CI green too.

This is not a restatement of a boundary — it is the opposite. `configs/agent/README.md` §5 names "narrow the matcher by one tool and every case still passes" and promises `check-agent-contract.py` is the seam guard for it; §6a claims G9 catches adopted-copy drift and "nothing else could." Both promises hold only for the template and the `.py` copies. **The one file Claude Code reads is the unchecked half of the adopted install.** The `#196`/`#182` incident class (append-only merge, profile narrowing) is precedent that settings wiring drifts by accident; this is its silent fail-open mirror, where `#196` was the loud fail-closed one. **Fix:** a G-check loading `.claude/settings.json` and asserting its parsed `permissions.deny` and PreToolUse matchers/commands equal the template's (JSON-equality, since key order legitimately differs), mirroring G9 — plus a mutation row in the checker's self-test.

### 4.2 A backslash-newline line continuation fails the no-verify guard open on the exact flag it exists to refuse
**Severity: high. Drift-reachable. Corpus case proposed and valid (`noverify-19-line-continuation.json`).**

`simple_commands()` splits the command on newlines (`no-verify-guard.py:135`) *before* lexing, then lexes each line with `shlex(posix=True)`. A shell line-continuation leaves a lone trailing backslash on line 1 (`git commit \`); `shlex` raises `ValueError`, `simple_commands()` returns `None` for the whole command (lines 140–141), and `main()` fails open with ALLOW (lines 243–245). Bash, meanwhile, joins the continuation and runs one hook-skipping `git commit … --no-verify`.

Reproduction: three continuation payloads all returned empty stdout (ALLOW) with stderr "the command could not be tokenised; allowing"; the single-line control was correctly DENIED. A shadowed-`git` argv proof confirmed bash runs `commit --no-verify -m wip` as one command. This is neither the indirection boundary (§3 — the literal flag *is* in the text) nor fully the untokenisable-fail-open concession (§4 — whose only example is an unbalanced quote, a command bash *itself* rejects; a continuation is well-formed and runs). It also defeats a capability the corpus advertises: `noverify-14` asserts multi-line detection works, and the very line-split that makes `noverify-14` pass is what orphans the backslash. **Reachability is drift** — a backslash-newline on a long `-m` message is ordinary agent formatting. **Fix:** fold `\`+newline continuations into one logical line before splitting/lexing; the doc note should distinguish this from the unbalanced-quote fail-open so a later reader does not re-file it under the conceded row.

### 4.3 A session launched in a subdirectory of an adopted repo carries none of the contract
**Severity: high. Drift-reachable. Corpus case: not expressible (same reason the deny rules are unfixturable). Surfaced during verification of a refuted claim.**

The original claim (that the `/`-anchor model is stale for worktree sessions) was **refuted**: on Claude Code 2.1.236 the leading-`/` anchor behaves exactly as `selftest.py`/README model it — denied at repo root, denied at a worktree root, and the docs sentence the claim leaned on is scoped to `settings.local.json`, not the project settings the guard ships. But the verifier's live probes turned up a different, real gap: `.claude/settings.json` loads only from the session's **primary working directory** with no parent-directory fallback, so a session launched in a subdirectory of an adopted repo loads **no deny rules and no hooks at all**. With `--add-dir ..` the verifier read and edited the protected `samples/expected/eslint.json` live, on disk, with zero refusal.

This is drift-reachable — it depends only on the directory a user launches `claude` in, no hostile intent — and it defeats the "outside the writable scope anyway" mitigation the anchor claim had assumed. It is a Claude Code settings-loading property, not a bug in the guard's Python, so the honest fix is a **documented-limitation sentence** (launch-directory scope) in `configs/agent/README.md`, plus optionally a dated live observation in §5a's style, and — if the platform offers one — a startup check. §5a's live evidence covers repo-root launches only, so nothing today records this.

### 4.4 A newline-separated gate declaration defeats the #178 partial-run guard
**Severity: medium-high. Drift-reachable, narrowly. Corpus case proposed and valid (`stop-30-a-newline-declared-gate-defeats-178.json`).**

`SHELL_OPERATORS` (`guard.py:288-289`) omits the newline, and `shlex` treats `\n` as whitespace so it never survives as a token. In `is_declared_gate()`, `shlex.split('python3 a.py\npython3 b.py')` flattens to a four-word list, the `any(word in SHELL_OPERATORS …)` check at `guard.py:372` finds nothing, and control falls through to `return ran == words` (`guard.py:374`) — so a receipt whose command is the one-line paste `python3 a.py python3 b.py` compares equal to the honest two-line declaration. This is the exact one-line-paste mistake #178 fixed for `&&`, left open for the newline separator. It is **not** the conceded "narrow the declaration" case: the declaration here is honest and complete; the partial run is measured against it and wrongly accepted.

Reproduction: unit — `is_declared_gate({'command':'python3 a.py python3 b.py'}, 'python3 a.py\npython3 b.py')` → `True` (the `&&` analog correctly → `False`). End-to-end — honest `--gate` on `gate_command="true\nfalse"` blocks; the attack `record-gate.py -- true false` runs only the first half, writes `verdict:pass`, prints **no** "not the gate" advisory, and Stop emits nothing (ALLOW). Both the Stop-time check and record-gate's advisory warning fail together, for the one reason. **Reachability is drift, but narrower than #178's:** it needs a consumer to declare a newline-separated gate (the `&&` form this repo uses is guarded) *and* the agent to use the documented `-- <command>` form instead of the instructed `--gate`, flattening two lines onto one argv. **Fix:** reject any declared gate containing a newline from the argv-equality path (or split on newlines and treat >1 command as `SHELL_OPERATORS` does), so a multi-line declaration can only ever be satisfied by the `bash -c`/`--gate` rendering.

### 4.5 Content inside an untracked embedded git repo is invisible to the fingerprint
**Severity: medium-high. Drift core, malice framing. Corpus case proposed but INVALID as written — needs a real gitdir.**

`git status --porcelain -uall` will not descend past a nested `.git` boundary, so an untracked embedded repo (a vendored dependency or cloned tool carrying its own `.git`) collapses to a single `?? vendor/` entry; `changed_files()` (`guard.py:178-216`) returns it as one path, and `fingerprint()` runs `git hash-object -- vendor/`, which fails on a directory, so the blob hashes to the constant `"absent"` (`guard.py:232-233`). The digest for that path is therefore fixed no matter what files live underneath, at both record and stop time.

Reproduction: with an untracked embedded `vendor/`, `changed_files` returned `['a.txt','vendor/']`; after `echo MALICIOUS > vendor/backdoor.py` (and after overwriting a pre-existing `vendor/lib.py`), the fingerprint was unchanged and the Stop hook emitted nothing (ALLOW). The verifier confirmed the load-bearing distinction: `-uall` **does** expand an ordinary untracked directory (its files hash and move the fingerprint) and does **not** expand an embedded repo — so the blind spot is specific to untracked *embedded repositories*. This is an **unlisted exception** to README §3's stated guarantee that shell-written content is caught because "the fingerprint moves" — a second class of shell write, besides the receipt, the fingerprint cannot see; the enumerated blind spots (gitignored files, receipt, `__pycache__`) do not name it. The security framing (plant a backdoor after the gate) is malice and out of scope; the **drift core is genuine** — an agent that vendors or clones a helper into a nested-`.git` subdir after running the gate ends the session with un-gated content on disk, no intent to hide. **The proposed fixture is invalid**: writing only `vendor/.git/HEAD` + `config` as plain files does not make git treat `vendor/` as a repo, so git expands it and the fixture passes green against the buggy code. A real gitdir (`objects/` + `refs/`, or `git init`) is required, and the case is then necessarily a RED test that belongs alongside the fix, not in the all-green corpus by itself. **Fix:** descend into untracked nested repos, or document the exception explicitly.

### 4.6 The ledger tripwire checks key names, not value shapes
**Severity: medium. Drift-reachable; needs a second drift for a public leak. Corpus case proposed but INVALID as written.**

`selftest.py:502-510` asserts each ledger row's keys are a subset of `{ts,outcome,blocked,changed,session}` and nothing more. `changed` is written as `len(changed)` today and `session` verbatim, but no fixture or runner assertion pins those value shapes. A drift-shaped edit that repurposes `changed` to a *list* of changed file paths — the natural "let's log which files" improvement — keeps the key `changed`, passes the tripwire, and carries private tree paths into the ledger.

Reproduction: the verifier patched a scratchpad copy of `stop-gate.py` to pass the list instead of `len()`, ran the full suite → `cases=68 failed=0`, and the mutated guard wrote a real path (`"changed": ["src/internal/Secrets.cs"]`) into the ledger. This defeats the ledger-file content contract `guard.py`'s docstring states ("never a path … or any text from the tree"), and **corrects an overstatement in README §6a1**, which says the corpus asserts "the key set, not only the values" — the outcome *values* are asserted via the ledger sequence, but `changed` and `session` values are asserted nowhere. Two tempering facts the original claim omitted, both verified: the ledger file is gitignored and per-checkout, and `--summary` (the pasteable artifact) prints no `changed` or `session` values, so a *public* leak needs a second, independent drift in `summarise()`. **The proposed fixture is invalid** — its `ledger_session_is_uuid` expect key is unimplemented and silently ignored, so it passes vacuously today. **Fix:** a value-shape assertion beside the key-set loop (`changed` is an int; `session`, when present, is a short id-like string with no `os.sep`), which the existing four ledger cases would then exercise. A per-case UUID assertion would be wrong on the merits, since Claude Code's session-id format is undocumented (README §6).

### 4.7 `assume-unchanged` / `skip-worktree` hides a tracked-file edit from the fingerprint
**Severity: medium. Hostile-by-command, or honest-by-environment. Corpus case proposed and valid, but needs a runner extension (`stop-31-assume-unchanged-hides-a-tracked-edit.json`).**

`changed_files()` derives its entire change set from `git status --porcelain`, and `stop-gate.py:238-242` short-circuits to the `clean` ALLOW on an empty set. `git update-index --assume-unchanged <f>` (index bit `h`) and `--skip-worktree` (bit `S`) both make git suppress a tracked file's modifications from status. A clean committed file edited afterward never enters `changed_files()`, the tree fingerprints clean, no receipt is required, and the session ends on content the gate never saw — falsifying the positively-stated guarantee in `stop-gate.py`'s docstring (lines 17–19) that "whatever wrote the bytes, they are in git status at the end of the turn."

Reproduction: after setting either bit and rewriting the file to contain `MALICIOUS_BACKDOOR`, `git status --porcelain` was empty, `git ls-files -v` showed `h`/`S`, and the Stop hook exited 0 (ALLOW) with no receipt. **Adversary model is split:** a forgetful agent does not type `git update-index --assume-unchanged` by accident (that reach is hostile), but these bits are a common developer-local trick to keep tracked config edits out of status — so in any consumer checkout where a file *already* carries the bit, an honest agent editing it is silently invisible to the gate (honest-by-environment). **Fix:** cross-check `git ls-files -v` and treat any path flagged lowercase (assume-unchanged family) or `S` (skip-worktree) as changed, or refuse the stop. The corpus case needs a one-line `selftest.py` `build()` extension to set the index bit; note the sharpening — `S` is uppercase, so the check must catch both cases.

### 4.8 A case-variant `file_path` defeats every `samples/` path check on a case-insensitive filesystem
**Severity: low-medium (bounded by the fingerprint + CI backstop). Malice-only. Corpus case proposed but INVALID as written (FS-dependent).**

On macOS's default case-insensitive FS, `os.path.realpath` (`sample-guard.py:170`) resolves symlinks but does not canonicalize letter-case, so `rel` (line 178) keeps the caller's casing and every downstream gate is a case-sensitive string op: the `samples/` gate (181), the `samples/expected/` gate (190), and `rel in cited_files(root)` (217). A path like `samples/typescript/src/BAD.ts` misses the exact membership test → ALLOW; `Samples/expected/eslint.json` misses even the outer gate → ALLOW; both open the same inode as the canonical tracked file.

Reproduction: a fixture-shrinking Edit via `BAD.ts` returned ALLOW (exact-case control DENIED); a manifest-emptying Write via `Samples/expected/eslint.json` returned ALLOW; `ls -li` confirmed the shared inode, and after the write `git status` reported the canonical lowercase path modified. **This is malice-only** — a forgetful agent edits the path it read (canonical case) and is caught; uppercasing a filename is a deliberate act. It lives *inside* the matched Edit/Write channel the hook claims to guard (unlike the conceded Bash-heredoc boundary), so it is a genuine implementation gap, but it is **backstopped**: the write lands on the canonical inode, so `stop-gate.py`'s fingerprint still moves at session end and `check-expected.py` still diffs the finding set in CI. It defeats the fast pre-write filter, not the whole guard. **The proposed fixture is invalid** on a case-sensitive FS (there the variant path is a genuinely different, non-existent file and allowing it is correct). **Fix:** case-fold the comparison when the FS is case-insensitive, or stat the target against cited paths (`os.path.samefile`) rather than comparing strings.

### 4.9 Two direct, fully-in-the-text hook-skip channels the no-verify guard does not model
**Severity: low-medium. Malice/evasion-reachable, not drift. Corpus cases proposed and valid.**

Two confirmed variants, both single commands with the hook-skip entirely in the literal text (so neither is the conceded indirection boundary), both reachable only by a session that knows the trick rather than one drifting toward `--no-verify`:

- **Unambiguous long-option abbreviation** (`noverify-19-abbreviated-no-verify.json`). `offending_flag()` compares the token to the exact literal `--no-verify` (`no-verify-guard.py:205-207`). Git accepts any unambiguous prefix, so `git commit --no-veri` (through `--no-verify`; `--no-ver` and shorter git rejects as ambiguous with `--no-verbose`) skips pre-commit. Reproduction: real git 2.50.1 committed with no pre-commit line; the guard emitted empty stdout (ALLOW) for `--no-veri` and `--no-verif`, full deny for `--no-verify`. **Fix:** recognize any `--`-token that is an unambiguous prefix of `--no-verify` (length ≥ `--no-veri`), on commit and push. The proposed "why" should say "match git's unambiguous abbreviations," not "match the prefix," since a bare prefix would wrongly flag `--no-ver`.
- **`git -c core.hooksPath=/dev/null commit`** (`noverify-20-hookspath-config.json`). `git_invocation()` treats `-c` as a global value-option and steps over it plus its value (`no-verify-guard.py:177-181`), so the hook-disabling config is never inspected. Reproduction: real git committed with the pre-commit hook fully bypassed; the guard returned ALLOW. The guard's own comment at lines 174–176 names this exact command — but only to justify stepping over `-c` so a *trailing* `--no-verify` still gets caught; it never notices `-c core.hooksPath=…` is itself a complete skip. **Fix:** when stepping over `-c`/`--config-env`, refuse if the value assigns `core.hooksPath`.

Both are evasion-shaped: the idiomatic drift reach is `--no-verify`/`-n` (both blocked), and `core.hooksPath` is the known move for getting *past* a guard that blocks `--no-verify`. Worth closing because they defeat the guard's own stated scope ("a commit may not skip the hooks"), but they should be filed as anti-tamper hardening, not as drift gaps.

### Restatements of the documented boundary (not findings)

Each of these reproduced exactly, but is a boundary the design already concedes in writing; they earn a line, not a fix.

- **Write of unparseable content empties a manifest** (`sample-guard.py:195-198`): the ValueError→ALLOW branch is in-source-documented and backstopped by `check-expected.py`, a required CI context that returns exit 3 on an unreadable manifest. A legitimate *tightening* exists — deny when `json.loads(proposed)` raises **and** the current manifest is non-empty, since total removal is evidence, not ignorance — but that is a change request, not a bypass.
- **`GIT_CONFIG_COUNT/KEY/VALUE` env injection of `core.hooksPath`**: real, but the same `core.hooksPath` channel as finding 4.9, unmodeled through *every* channel, and malice-only. If widened, model `core.hooksPath` once across `-c`, env, and local config, not this one spelling.
- **A lost ledger write undercounts blocks undetectably** (`guard.py:141-147`, bare `except Exception: pass`): explicitly "fail open, harder than anything else here" in both the docstring and README §6a1; the refusal is emitted before `record()` runs, so enforcement is never weakened. In scope as an honest caveat, not a defect.

### Refuted, for the record

- **Session-id copied verbatim into the ledger**: the low-level observation is true (`stop-gate.py:154-156` copies `session_id` with only an `isinstance` check), but the "safe to paste by construction" promise attaches to `--summary`, which prints only a session *count* — verified against a poisoned ledger. Malice-only (a real hook gets its id from Claude Code). The genuine residue is that **no corpus case exercises `--summary` at all**, so nothing would catch a future `summarise()` edit that starts printing session values — see §7.

## 5. The concept judged

**Is "gate-seen content" the right invariant? The unit is right; the trigger granularity is the conceptual weakness.** A gate's output is a function of the whole tree — a change in file A breaks the check in file B — so the whole-tree, all-or-nothing fingerprint is not conservatism, it is the only sound granularity for the cross-file gates this repo ships (tsc, Roslyn, mypy, test suites). "Gate-seen-per-file" would be unsound. The pre-run fingerprint is the detail that makes the unit honest.

The weakness is that a `Stop` hook fires at the end of *every assistant turn*, not at session end. So the invariant as implemented is "Claude may not pause the conversation on unseen content," which produces false refusals: a WIP handoff ("here's a draft, which direction?") on a dirty tree is blocked; a nondeterministic gate (timestamps, lockfiles) produces a permanently stale receipt and never converges; a stray scratch file forces a full re-run. For this repo's seconds-long gate the tax is invisible; for a consumer whose honest gate is lint + full tests it is minutes of latency on every pause, and that is the pressure that will push gate-narrowing. The pressure is **not hypothetical**: this repo's own declared gate is already narrowed from the 28-context `ci.yml` to `selftest.py && check-agent-contract.py` "for cost reasons" (README §6a) — the first and only adopter declared a partial gate on day one. That is not damning (a narrowed-but-honest gate beats no gate), but it means "gate-seen" quietly means "declared-gate-seen," and the declaration is a session-writable, cost-pressured string. This should be said plainly wherever the guard is described. The genuinely better formulation is a refinement, not a replacement: fire the full check at **commit and session-end**, and let the per-turn Stop check degrade to something cheap or nothing.

**What it misses entirely.** The guard covers exactly one meta-failure well — *claimed verification that did not happen* — plus two narrow tampering shapes and a hook-bypass flag. Everything semantic is untouched: silently weakened assertions, a fix claimed but not tested, deleted tests in the consumer's own suite, over-broad refactors, scope creep, behavior regressions on untested paths. Most of that is fine and honestly admitted — closing it would make the guard a code reviewer, a different and worse project. Two items are not fine:

1. (#213) **The weakened-assertion case is the sharpest criticism of the whole idea.** Everywhere else the guard is orthogonal to a failure; here it is *adverse*. A session that weakens a consumer's test (`toBe(x)` → `toBeDefined()`) and then dutifully runs the gate ends with a passing receipt, and "gate-seen" reads to a human as "verified." The receipt certifies **execution, never adequacy** — and nothing in the consumer-facing prose says that as bluntly as it says the receipt-forging limit. This is UNMEASURED (a design argument, not a detection claim), but it is the residual risk the honesty in the README is load-bearing against.
2. (#214) **The repo's own top-ranked catastrophic failure is unguarded.** CLAUDE.md §2 is unambiguous that the one unrecoverable failure here is a real consumer name reaching a public commit message, PR body, or issue — "there is no cleanup pass." The ledger's key-set assertion guards this for the ledger; nothing guards it for commit text, which is where it would actually happen. A pre-commit tripwire greping the commit message and staged diff against the real names (kept in a gitignored, never-committed file) would be ~30 lines and, by the repo's own risk ranking, buys more than `sample-guard.py`'s 234. UNMEASURED — design argument.

**Is it worth its cost?** Yes on the core, and the cost that matters is not the ~2,000 lines but the incident burn rate. Against the house's three tests: detection proof is **strong** (68 fixtures, mutation tables, the best-evidenced config in the repo); in-house demand is **genuine** (#193's "one solution for all my repos," ~45 of them); adoption-cost proof is **absent**, the same empty cell as Java's, correctly labeled. That is the profile the repo ships other configs at. But roughly a dozen guard-lineage issues landed in one month, and the install/mode machinery produced nearly all of them — including #196, where the guard *bricked a repo* (every Bash/Edit call failing) and the broken state reached a consumer's default branch. **The complexity is compounding at the adoption seam, not the enforcement core.** The concept judge's recommendation, which this review endorses, is to keep the invariant, the receipt, the two deny rules, and the no-verify guard, and to seriously weigh **deleting `sample-guard.py`**: it duplicates `check-expected.py` (which CI runs and which catches strictly more, including the in-place defusal the hook concedes it cannot see), it is inert in most consumers (#182), it was 43% of the dead weight #191 removed, and its wiring produced the #196 class — while `Edit(/samples/expected/**)` plus CI still hold the actual line. That is a judgement for the owner, not an action this review takes.

## 6. The measurement contract judged

**Will #167 produce a decision, and by when? As it stands, no — and never, at the observed rate.** Measured on this checkout on 2026-08-30 (`stop-gate.py --summary`): 3 sessions, 16 stops, **0 blocked**, all 16 outcomes `clean` with `changed: 0`, zero `pass` outcomes. The Stop gate's *enforcing* path has been exercised zero times in real use — only the fixtures have ever seen it fire. Every stop happened on a tree identical to HEAD, which is what you get when work is committed before stopping (the pre-commit hook forces the gate at commit time, so the tree reads clean at stop time). Two days of dogfooding measure the guard's overhead (none) and nothing about its judgment.

Three structural problems:

- **No threshold exists anywhere.** #167 asks for "four integers and a period" but names no period length, no minimum session count, no stopping rule. UNMEASURED-forever is indistinguishable from measured-and-fine unless the number is written down first.
- **The ledger is running in the wrong repo for #167's purposes.** The acceptance criteria are about the Consumer-A adoption-cost cell; the guard "has never run in a consumer" (README §6). This baseline's ledger can only ever fill a "baseline dogfood" row.
- **#167 is administratively closed by the same GitHub keyword bug it documented at #178.** PR #205's merge commit `ceffd3b` contains the sentence "This does not close #167," and GitHub's closing-keyword regex matched `close #167` anyway. None of #167's four acceptance criteria are met on `main`: STATUS.md §5 has no agent-surface row, and `configs/agent/README.md` §6 still literally says "That has not happened." This is the subagents' assessment, relayed for the owner to act on — the likely action is reopening #167 or filing a fresh issue for the actual measurement period. **This review did not reopen or edit anything.**

**Is it measuring the right thing?** Partly, and the gap should be stated rather than papered over. A *correct block* is the value event and is a lower bound on caught incidents (minus loop-guard/8-block escapes, which are countable from existing data as a block→loop-guard sequence in one session). What the four numbers cannot decide: total value, deterrence (a session that runs the gate *because* the guard exists leaves the same trace as one that would have anyway — unmeasurable without a control arm), or whether the Stop gate is redundant with the commit hook. In this repo the pre-commit hook makes trees clean before stop, so the Stop gate binds only on sessions ending with uncommitted work — a population empty for two days; in a consumer without `--hooks` it would bind far more often, so the row must say which profile the consumer ran. The four numbers are enough to decide keep-vs-remove on cost grounds, which is what an adoption-cost cell is for; the cell should not claim more.

**The falsifier is missing.** No observation is currently pre-committed to kill the guard, which makes the measurement decorative in the precise sense that matters. It should be named before data arrives: primary — over the pre-registered period, `blocks wrong > blocks correct`; instant — one wrong block that wedges a session beyond self-repair (the #196 shape) is removal-grade regardless of ratio; qualitative — #167's own line answered "yes, a contributor who did not choose this would have switched it off." And the explicit **non-falsifier**, stated in advance: `0 correct / 0 wrong` over the whole period does *not* falsify — it is ambiguous between deterrence, redundancy with the commit hook, and a quiet period — its consequence is a longer period or a different consumer, not a verdict. Pre-registering this matters most because 0/0 is where the data is currently heading.
